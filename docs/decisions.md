# 결정 기록 (프런트 연동 API 작업)

형식: `D-<번호>: 질문 / 선택 / 이유 / 날짜`. 번복 시 번호를 언급하고 이유를 쓴다.

## 지시로 확정된 것 (선택지 없이 사용자 지시)

- **D-0.1**: admission queue·RAM 프로파일·Redis 를 이번 작업에서 뺄까? / 전부 `legacy/` 로 이동, `/ask` 는 동기(서버 타임아웃 180초), 202 경로 제거 / 프런트 연동 범위를 줄이고 계약을 단순하게 / 2026-09-27 (커밋 `9ab6d0b`)
- **D-0.2**: hosted LLM provider 를 어떻게 고를까? / `.env`(`RFA_LLM_PROVIDER=nvidia|gemini`, `RFA_LLM_MODEL`, `RFA_LLM_BASE_URL`)로 선택. 두 provider 모두 OpenAI chat.completions 로 호출하고 프록시가 요청 필드 allowlist·응답 정규화로 동일하게 맞춘다 (`proxy.upstream_payload` / `normalize_completion`). 두 프리셋 모두 reasoning 을 끈다(NVIDIA `enable_thinking=false`, Gemini `reasoning_effort=low` — `none` 은 3.5-flash-lite 가 400). Gemini 는 `GEMINI_MODEL` 로 `gemini-3.5-flash-lite`(기본) | `gemini-3.8-flash` 두 모델만 제공, nvidia 는 `NVIDIA_MODEL`. 라이브 확인: 프록시 경유 internal 1.6초 allow, external 2.9초 요청 마스킹 4건 / 사용자가 Gemini API 로도 호출하길 원함 / 2026-09-27
- **D-0.3**: 검열 LLM 판정이 턴마다 3~4회, hosted 호출 1/4 이 45초까지 멈춤 → 어떻게 줄일까? / 요청 측 판정은 가장 새로운 non-system 메시지 1회, 응답 측은 regex 만, 최종 답변 판정 1회 유지. 타임아웃 45→12초 + 1회 재시도, 두 번 다 실패하면 그 텍스트는 regex 결과로 통과(`on_error: allow`, 감사에 degraded) / "호출이 안 되면 해당 provider 를 빼버려" — 사용자 지시. 실측: summarizer 턴 53초 → 12초 / 2026-09-27
- **D-0.4**: 사내/사외 등급은 무엇의 속성인가? / 태스크가 아니라 태스크 아래 들어오는 요청(결재 대상)마다 매긴다. 값은 `사외`(audience public)·`사내`(company/self). 태스크·에이전트 API 에 등급 필드를 두지 않고, 채팅은 질문 1건 = 요청 1건으로 역할이 등급을 정한다(owner→사내, guest→사외) / 시안 2차 판 + 사용자 지시("등급이 task 단위가 아니라 task 하위 요청들 단위") / 2026-09-28

## 대화로 정할 것

- **D-1 스트리밍 방식**: 토큰 스트리밍(게이트웨이 HTTP) vs 문장 단위 의사 스트리밍? / **둘 다, 병렬 트랙**. SSE 계약은 A(의사 스트리밍: `run.started → stage → delta… → guard.final → done`, 봉투 `{type,runId,seq,ts,data}`)로 지금 구현하고, B(샌드박스 게이트웨이 `/v1/chat/completions` HTTP 전송)는 브로커 전송 교체로 병렬 진행. 성공하면 delta 공급원만 교체(owner 만 토큰, guest 는 검열 후) / 실측: 턴 14.8초 중 모델 호출 4.2초, 나머지 ≈10초가 `nemoclaw agent` CLI 경로 오버헤드 → B 는 스트리밍보다 지연 제거가 본질. 사용자: "그렇게 오래 걸릴 작업이 아니다, 병렬로" / 2026-09-28
- **D-2 guest 검열 위치**: D-1 A 트랙 결과 delta 는 이미 검열 후 텍스트 → "완료 후 일괄(regex+LLM 1회) + `guard.final` 1회"가 사실상 확정. B 트랙(게이트웨이 HTTP)도 프록시가 상류를 버퍼링해 토큰 단위 delta 가 아직 없음. **제안: 이대로 확정.**
- **D-3 선택지 수위**: 샘플 `.local/d3/samples.json`(규칙 vs 프롬프트, 2026-09-28 01:35). 규칙 방식은 `[수치]` 구멍·누락(88.4 %)·주소 방치, 프롬프트 방식(gemini-3.5-flash-lite 1.8초)은 세 수위가 자연스럽고 주소·이메일을 스스로 제외. **추천: 프롬프트가 생성, 규칙이 검증**(T1 에 수치·일자·방향어 없음, T2 에 수치·일자 없음, 전 수위 주소·이메일 없음 → 위반 시 옵션 폐기 + 재생성 1회). 미결.
- D-4, D-8, D-9: 미착수.

### 「검색하거나 물어보기」·「태스크 추가」 (`docs/FE_CHAT_TASK_API_PLAN.md`, 2026-09-28)

사용자: "아래 명시 안 된 건 전부 추천으로 진행" → D-10·D-5·D-14·D-15·D-7 은 추천안, D-12·D-13·D-6 은 사용자 지정.

- **D-10 대화 상대 = ?** / task 1개 = 대화 상대 1개(시안의 태스크:에이전트 1:1). `ask.yaml` 카탈로그 + 팀이 원천이고 아이콘·색·desk·태그·추천 질문 등 표시 메타는 SQLite `tasks` 로 덧씌운다 / 시안 규칙과 head 카탈로그 단위가 같다 / 2026-09-28
- **D-5 지정 대화(`agentId`)** / head 를 건너뛰고 그 task 로 바로 위임(후보 1개, score 1) / 사용자가 이미 담당자를 골랐다 / 2026-09-28
- **D-12 여러 담당자 위임** / 상황에 따라 1명 또는 여러 명 동시. 입력 context 에 대한 담당자 탐색(head)이 후보마다 점수(0..1)를 매기고 **threshold 이상인 후보 전부**를 병렬 위임한다. 모두 threshold 미만이면 담당자 없음(D-13). threshold·최대 동시 수는 `ask.yaml head` 설정 / 사용자 지정 / 2026-09-28
- **D-13 담당자 없음·일반 질문** / 비서가 직접 답한다. 조건은 hallucination 금지 하나: 근거 없는 사내 정보(프로젝트·수치·일정·사람·문서)는 추측하지 않고 "알 수 없다"고 답한다. 위임 결과를 합칠 때도 담당자 답에 없는 내용은 만들지 않는다. 등급 검사는 그대로 거친다 / 사용자 지정 / 2026-09-28
- **D-14 trace 노출과 검열** / 사외(guest) 질문에는 `delegate.log`·`summary` 를 정해진 문구로만 보내고 원문은 사내(owner)에게만 / 검열 전 원문이 진행 과정으로 새는 것을 막는다 / 2026-09-28
- **D-15 `delegate.log` 공급원** / 서버 단계 로그로 시작, D-1 B 트랙(게이트웨이 스트림)이 붙으면 도구 호출 로그로 교체 / 2026-09-28
- **D-7 대화 저장** / owner 대화만 SQLite 저장, guest 는 클라이언트가 들고 `history` 로 보낸다 / guest 는 신원이 없다 / 2026-09-28
- **D-6 태스크 생성** / `POST /tasks` 를 스트리밍(SSE)으로: 요구사항 분석 → 팀 설계(실제로는 패턴 선택) → spawning(선언·`agents apply`·시드) 진행을 단계별로 보여 준다 / 사용자 지정("과정을 보여줘야 함"). 팀 생성은 최대 300초라 결과만 기다리게 할 수 없다 / 2026-09-28

### 「에이전트」·「샌드박스」 관리 화면 (`docs/FE_ADMIN_API_PLAN.md`, 2026-09-28)

- **D-16 샌드박스 목록 단위** / 실제 선언된 샌드박스(`assignments.yaml`: rfa-main L2, rfa-tasks-none L0)를 보안 그룹·권한 레벨과 함께. 시안의 등급 4단(공개/회사/사업부/업무) 타일은 쓰지 않는다 / 등급은 요청 단위(D-0.4)이고 실제 배치와 맞아야 한다 / 사용자 선택(추천안) / 2026-09-28
- **D-17 에이전트 목록 단위** / 백엔드 에이전트 전부. 태스크 에이전트(태스크 담당·팀 supervisor·팀 멤버·task 에이전트)를 먼저, 관리 에이전트(assistant·censor)를 뒤에. 관리 에이전트는 변경 불가, 힌트 「데모에서는 관리 에이전트를 수정할 수 없습니다」 / 사용자 지정 / 2026-09-28
- **D-18 관리 화면 동작 범위** / 조회는 전부. 즉시 적용만 실제 동작: 추론 제공자·모델 전환(프록시 라우팅을 실행 중에 교체 + `.env.dev` 에 기록), 대화 압축·기억 비우기(샌드박스 안 세션·기억 파일), 시스템 프롬프트 추가 지시·불러오는 자료(IDENTITY.md 다시 올림). 컨텍스트 길이·최대 응답 길이는 저장만 하고 「다시 만들 때 적용」 대기로 표시. 샌드박스 추가는 한도(2개) 안내만 / 사용자 선택(추천안). 재생성은 2~4분·≈2 GiB·상태 파괴 / 2026-09-28
- **D-19 컨텍스트 사용량 출처** / 프록시 실측: 모든 LLM 호출이 egress-proxy 를 지나므로 요청을 시스템 프롬프트·도구 정의·기억과 노트·대화 기록으로 나눠 토큰을 추정하고, 응답 `usage.prompt_tokens` 가 있으면 합계를 그 값에 맞춘다. 에이전트의 마지막 호출 기준. 호출 통계(호출 수·토큰·평균 응답·차단)도 같은 감사 기록(`inference`)에서 계산 / 사용자 선택(추천안) / 2026-09-28

### 결재 프로세스 (RFA_module 연동, `docs/FE_APPROVAL_API_PLAN.md`, 2026-09-28)

- **D-20 결재 상태의 주인** / RFA_module 결재 서버(:8790)가 상태·게시를 계속 맡고, rfa_mas 는 프런트용 결재함 API 로 그 서버를 읽고(목록·상세) 쓴다(응답 = approve, 재생성 = reject+사유). rfa_mas 는 자기가 아는 것(단계·검열 결과·소스 등급·담당 에이전트)을 보태고 owner 권한을 건다 / 게시 코드·토큰이 RFA_module 에만 있고, RFA_module 은 HEAD_URL 한 줄만 바꾸면 된다 / 사용자 선택(추천안) / 2026-09-28
- **D-21 RFA_module 요청 수신** / `POST /v1/head/ask` 를 RFA_module head 계약 v0.2.0 그대로: 인증 없이 루프백만, `request_id` 는 서버가 `url`+차수로 만들어 재시도에 멱등, `refusal` 은 문자열, 크기 초과는 잘라서 처리, 서버 한도 110초(RFA_module 클라이언트 120초 안). 기존 `/ask`(토큰) 는 그대로 / 사용자 선택(추천안) / 2026-09-28
